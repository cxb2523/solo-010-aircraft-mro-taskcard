# 航空机务工卡执行与放行台子

把“一摞纸、签完字谁改了什么查不出来”的机务维修工卡搬上台子：按依赖顺序放行执行、
双人签会签、按工种校验人员资质、耗材从库房台账实时扣减、缺件/复查两类保留项全程跟踪，
签字事件**只能追加、不能改旧记录**，写错只能追加一条冲正（correction）并回链原记录。

- 后端：Node 20，**零第三方依赖**（仅 `node:http` / `node:fs` / `node:path` / `node:crypto`）
- 前端：普通 HTML/CSS/JS 页面，无构建、无框架、无 CDN
- 启动：`node server.js`（或 `npm start`），浏览器打开 <http://localhost:8080>
- 端口可用环境变量覆盖：`PORT=9000 node server.js`

## 目录结构

| 路径 | 说明 |
| --- | --- |
| `data/cards.json` | 6 份工卡（4 例行 + 2 排故，每份 12–13 步）：工卡号、机型、专业、计划完工时间；步骤含步骤号、内容、依赖步骤号、需要工种、是否双人签、耗材 |
| `data/deps.json` | 步骤先后依赖的权威清单（启动时与 `cards.json` 交叉校验）、保留项台账、库房台账期初数量 |
| `data/staff.json` | 5 个工种代码、9 名人员及其资质条目（证件号、到期日） |
| `data/events.jsonl` | 运行态：只追加的签字事件流（首启自动创建；`reset` 自动备份后清空） |
| `server.js` | 零依赖后端：静态页面 + JSON API + 事件溯源状态机 |
| `public/` | 前端页面（`index.html` / `styles.css` / `app.js`） |

## 放行口径（本系统的关键判断）

“所有步骤签完就算放行”还是“保留项、复查、资质全部对得上才算放行”？
两种口径在当前样例下放行数量不同（初始状态为 0；步骤签完后，仅复查超期的
`RC-2026-0902` 在宽松口径下可放行、严格口径下不可放行）。

**本系统实现并采用严格口径（strict）**，一份工卡必须同时满足以下条件才能“报完工/放行”：

1. 每个步骤要么已签署完成、要么是排故工卡中经放行人员批准、写明原因的合规跳过；
2. **缺件等件类保留项全部关闭**——缺件没到，被阻塞的步骤签不了，整卡也放不了；
3. **到期复查类保留项不处于超期状态**——复查到期当天（含）允许完工，一旦超期整份工卡不许报完工，
   完工按钮直接置灰并列出是哪条复查超期；在期内的复查保留项不拦截；
4. 每条签字的签署人**当前仍持有该步骤要求工种的有效资质条目**（证件到期次日起失效）。

宽松口径（loose）只看第 1 条，系统同时计算并在工卡列表上显示两种口径各自的可放行数量，
用来直观展示“差不少”的差异。

**为什么选严格口径**：机务维修的放行结论直接关系到适航与飞行安全。缺件保留项意味着飞机带着
已知偏差，到期复查超期意味着维修方案规定的持续监控失效，证件失效意味着签名本身不具备授权——
这三类问题都不会因为“纸面步骤都签了”而消失。步骤签完只是施工完成，**适航放行必须在施工完成之外
再确认无未闭合风险**，因此采用严格口径；同时保留冲正/补复查/到货入库等正规途径把问题真正闭合，
而不是放行时放水。

## 执行与签字规则

- **依赖顺序放行**：前置步骤未签署（或未合规跳过）时，后续步骤在页面上置灰，签字接口直接拒绝并
  写明“缺少前置步骤 X 的有效签署”。
- **双人签**：标记 `requiresDual` 的步骤必须两名**不同的**、都持该工种资质的人分别签，
  签在同一条签署记录里；第一签后记录处于待会签状态（耗材暂不扣），第二签完成才算完，
  同一人签第二下会被拒绝。
- **指定工种**：每个步骤要求一个工种，签字实时比对人员资质；没有该工种条目的签名一律拒绝，
  错误信息指出“人员 X 的资质台账中没有『工种』条目（资质要求条目：trade=…）”，证件过期同样拒绝。
- **耗材与库房台账**：单人签在签署时、双人签在第二签完成时扣减；会把台账扣成负数的请求一律拦截，
  提示需要数量和当前余量。冲正已完成记录时耗材按原数量回补。
- **排故跳过**：仅 `troubleshooting` 工卡中标记 `skippable` 的步骤可跳过，必须填原因并由持
  “放行”授权的人员批准；可再由放行人员撤销跳过。例行工卡任何步骤都不允许跳过。
- **签字只追加**：`data/events.jsonl` 只追加写入，从不修改或删除旧行。写错内容不能改旧记录，
  只能由原签署人或放行人员追加一条 `correction` 事件（必填原因），原记录被标记为已冲正并
  指向冲正事件，步骤恢复为可签状态；时间线里旧签字保留并显示删除线。

## 保留项（两类）

- **缺件等件（part）**：开放时阻塞其绑定步骤的签字（如 `RT-PART-001` 阻塞 `TR-2026-1107` 第 6 步）。
  在“保留项台账”里登记到货入库（入库单号、数量）后保留项关闭、物料入台账，步骤解除拦截。
- **到期复查（review）**：带 `dueDate`。页面/接口按当天日期给出“在期 / 今日到期 / 已超期”状态；
  超期时整份工卡完工按钮置灰。登记复查完成（需工卡专业资质或放行授权）后保留项关闭。
  复查判断在每次请求时读取 `data/deps.json` 现算，**把 `dueDate` 改成昨天立即生效，无需重启**。

## 样例里预先埋好的“坑”

| 坑 | 位置 | 现象 |
| --- | --- | --- |
| 前置没签就想签后面 | 每份工卡的依赖链（如 `RC-2026-0901` 直接签第 2 步） | 拒绝并指出缺第 1 步 |
| 复查超期 | `RT-REV-002`（`RC-2026-0902`，应于 2026-09-21 复查，系统日期 2026-09-22） | 全卡不许完工，按钮置灰并给出原因 |
| 今日该复查 | `RT-REV-003`（`RC-2026-0906`，dueDate=2026-09-22） | 列表“今日该复查”筛选可见，严格完工前需先复查 |
| 缺件拦截 | `RT-PART-001`（PRV，库存 0，阻塞第 6 步）、`RT-PART-004`（剪销，阻塞 `TR-2026-1112` 第 7 步） | 件未到签字被拒 |
| 资质不够 | `S002 李伟`只有机械资质，让他签电子/无损/放行步骤 | 拒绝并指出缺哪条资质；`S005 刘洋`电子证件 2026-09-23 到期可验证临期 |
| 扣成负数 | `MAT-TIE-WRAP` 扎带库存 3，`RC-2026-0906` 第 9 步需要 5 | 扣减被拦截 |
| 双人签 | 各工卡倒数第 2 步（如第 11/12/13 步的复核） | 一人签不完，同一人不能签两下 |
| 排故跳过 | `TR-2026-1107` 第 5、7 步，`TR-2026-1112` 第 5、10 步 | 须填原因 + 放行人员批准 |

## 页面

- **工卡列表**：工卡号、机型、专业、类别、计划完工时间、步骤闭合进度、两种口径可放行状态、
  超期/今日复查/缺件角标；筛选含“今日该复查 / 复查已超期 / 有缺件保留项 / 例行 / 排故 / 宽松能过严格不能过”。
- **单份工卡步骤树**：前置未闭合的步骤置灰；每一步显示谁、在什么时候、以什么工种签的，
  耗材扣了什么；双人签显示待会签；右侧为该卡全部事件的时间线（签字、会签、冲正、跳过、保留项开闭、放行）。
- **人员与资质面板**：工种代码、人员证件号与有效期，过期证件标红。
- **保留项台账**：两类保留项状态筛选、到货/复查登记操作，下方为库房台账实时余量。
- **签字记录页**：全部事件按时间往下滚（可按工卡过滤），旧记录不可改；含一键清空恢复样例（自动备份）。

## 验收操作指引（对照题目两条验收标准）

1. 打开 <http://localhost:8080>，进入 `RC-2026-0901`，直接点第 2 步“签字” → 被拦截并提示缺第 1 步；
   签第 1 步后再签第 2 步 → 通过。
2. 进入 `RC-2026-0902`（工卡列表带“复查超期”红标），把步骤全部签完（第 5、12 步需两名电子员
   分别会签），“报完工/放行”按钮始终置灰，下方红字给出“复查保留项 RT-REV-002 已超期……”。
   也可直接把 `data/deps.json` 里 `RT-REV-003` 的 `dueDate` 改成昨天保存，刷新页面即看到
   `RC-2026-0906` 完工按钮变灰并给出原因。
3. 其他：签字人选择时点“取消”可从全部人员里挑无资质者验证资质拒绝；`TR-2026-1107` 第 6 步在
   PRV 到货登记前签不了；排故步骤跳过需放行人员批准；签错可“冲正”，记录页能看到原行保留+
   追加的 correction 回链。

## HTTP API 摘要

- `GET /api/overview` 工卡列表 + 两口径计数；`GET /api/cards?cardNo=...` 单卡（含步骤状态与时间线）
- `GET /api/staff`、`GET /api/retains`（含库存）、`GET /api/events?cardNo=...`
- `POST /api/sign` `{cardNo, stepNo, staffId}`（双人签同一步骤调用两次）
- `POST /api/correct` `{cardNo, stepNo, recordId, staffId, reason}`
- `POST /api/skip` / `POST /api/unskip` `{cardNo, stepNo, approverId, reason?}`
- `POST /api/retains/arrived` `{retainId, staffId, qty, grn}`、`POST /api/retains/reviewed` `{retainId, staffId, result}`
- `POST /api/release` `{cardNo, staffId}`、`POST /api/reset`
